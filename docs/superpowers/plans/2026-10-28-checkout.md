# Checkout personalizável — plano de implementação

Objetivo: permitir que cada projeto venda ofertas avulsas ou planos pelo seu próprio checkout, com marca e cores configuráveis, sem expor a chave secreta ou trafegar cartão no backend.

Decisões delegadas: reutilizar Go/Postgres/Bootstrap; primeira integração de checkout com cartão Pagar.me e chave pública cadastrada no painel. Stripe continua disponível na API de cobrança existente; seu checkout exige uma integração própria de autenticação adicional e fica fora desta entrega. Não receber PAN/CVV no servidor.

Fluxo: integração autenticada cadastra oferta (preço em centavos, créditos ou plano existente), cria sessão com cliente/referência e recebe caminho /checkout/{token}. Sessão expira em 24h; preço e identidade visual são fotografados na criação. Comprador informa seus dados e cartão; navegador tokeniza diretamente no Pagar.me. Servidor cria cliente/cartão no provedor e enfileira uma única cobrança, usando o worker existente. Para recorrência exige consentimento explícito e cria assinatura com primeiro ciclo imediato. Tela acompanha confirmação real. Saldo só muda após confirmação pelo provedor.

Identidade: nome, descrição, logo HTTPS, cor de fundo e cor principal com texto de contraste calculado. Layout de duas colunas: resumo e periodicidade à esquerda, identificação/endereço/cartão à direita; uma coluna no celular; tema escuro por padrão. Sem scripts/CSS arbitrários ou marca Payment Hub no checkout. Uso no domínio do SaaS por proxy da rota /checkout; link compartilhável também disponível. Não incluir iframe ou domínio customizado automático.

Superfície pública: somente /checkout e assets próprios passam no proxy, junto do webhook existente. Console/admin/API permanecem privados. Token aleatório de 256 bits; respostas sem segredo ou dados pessoais; cache desabilitado; sem fontes/scripts externos. Chave pública não é segredo. Validação de preços no servidor, isolamento de tenant, bloqueio de reenvio concorrente e confirmação independente do webhook.

- [x] Banco e API: branding, ofertas imutáveis, sessões idempotentes, snapshots, expiração. Testes de isolamento e preço.
- [x] Recebimento de token: cliente/cartão Pagar.me, consentimento, única cobrança/assinatura transacional. Testes com servidor simulado, falhas e concorrência.
- [x] Checkout responsivo e painel: configuração, ofertas e geração de links. Validar no navegador sem dados reais.
- [x] Proxy, documentação de integração e teste de rotas públicas; suíte Postgres/race; build e execução local.

Riscos e validação pendente: tokenização real requer pk_test e domínio autorizado no painel do Pagar.me. Captura de cartão deve ocorrer apenas via HTTPS em produção. Configuração de autenticação dos webhooks continua independente.

Entrega executada; validação real da tokenização aguarda chave pública e domínio autorizado. API e navegador validados com provedor simulado; nenhum pagamento real foi realizado nesta etapa.
